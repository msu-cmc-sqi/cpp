# Урок 4. CMake, многофайловый проект и JSON

## Цель занятия

Собрать программу из нескольких файлов и библиотечной цели, запустить её тесты одной командой и безопасно преобразовать JSON в типы C++. Эти навыки понадобятся для собственного приложения с локальной моделью. Сначала разберём сборку, затем подключение внешней библиотеки и границу между JSON и прикладной логикой.

## 1. От исходников к исполняемому файлу

Компилятор обрабатывает каждый `.cpp` отдельно. Заголовок сообщает об объявлениях; реализация функции из другого `.cpp` попадает в программу на этапе компоновки. Поэтому `#include "model_config.hpp"` **не заменяет** добавления `model_config.cpp` в сборку. Ошибка `undefined reference` или `undefined symbols` часто означает, что нужный `.cpp` не включён в цель или библиотека не подключена к ней.

Разделяйте файлы по ответственности:

```text
project/
├── CMakeLists.txt
├── include/model_config.hpp  # публичные объявления
├── src/model_config.cpp      # реализация
├── src/main.cpp              # CLI и вывод
└── tests/config_test.cpp     # проверка логики без модели
```

В заголовке используйте `#pragma once` или защитный макрос. Подключайте только нужные заголовки. Публичные имена удобно поместить в `namespace model_config`, чтобы они не конфликтовали с именами других частей проекта. Не добавляйте `using namespace std;` в заголовок: он меняет пространство имён каждого включающего файла.

## 2. Что такое Make и CMake

**Сборка** превращает исходные файлы в программу: сначала компилятор получает объектные файлы из `.cpp`, затем компоновщик соединяет их с библиотеками. Для проекта из многих файлов важно знать, в каком порядке выполнять команды и что нужно пересобрать после изменения исходника.

**Make** — программа, которая выполняет правила сборки из `Makefile`. Правило называет результат, его зависимости и команду. Например:

```make
hello: main.cpp
	c++ -std=c++17 main.cpp -o hello
```

Команда `make hello` создаст исполняемый файл. Если `main.cpp` изменится, Make выполнит правило снова; если ничего не изменилось, пропустит его. Для многофайлового проекта правил становится больше: отдельно компилируются `.cpp`, затем объектные файлы соединяются в программу. Make нужно понимать на этом уровне, даже если `Makefile` мы не пишем вручную.

**CMake** — инструмент для *описания и настройки* сборки. В `CMakeLists.txt` мы задаём цели (исполняемые файлы и библиотеки), их исходники и зависимости. CMake на основе этого описания создаёт файлы для выбранной системы сборки: например, `Makefile` для Make или `build.ninja` для Ninja. Он может также создать проекты для Visual Studio и Xcode. CMake сам не заменяет компилятор.

Схема процесса: `CMakeLists.txt` → `cmake -S . -B build` → файлы сборки в `build/` → `cmake --build build` → компиляция и компоновка. При генераторе Make последняя команда вызывает Make; можно явно выполнить `make -C build`. Команда `cmake --build` удобна тем, что не зависит от выбранного генератора.

Три шага из корня проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
```

`-S` указывает каталог с корневым `CMakeLists.txt`, `-B` — каталог для сгенерированных файлов. `Debug` помогает при отладке; для конфигураций Visual Studio и Xcode укажите также `--config Debug` при сборке и тестировании. Папку `build/` не добавляют в Git. После изменения `CMakeLists.txt` повторите конфигурацию; при обычном изменении `.cpp` достаточно повторить сборку.

### Первая цель

```cmake
cmake_minimum_required(VERSION 3.20)
project(hello_cmake LANGUAGES CXX)

add_executable(hello src/main.cpp)
target_compile_features(hello PRIVATE cxx_std_17)
```

`project` задаёт имя проекта и язык; `add_executable` создаёт цель `hello`. `target_compile_features` требует C++17 именно для этой цели. Исходники перечисляются явно: видно, когда новый файл забыли добавить.

### Библиотека и тест

Когда логика нужна и программе, и тесту, поместите её в библиотеку:

```cmake
cmake_minimum_required(VERSION 3.20)
project(model_config LANGUAGES CXX)

add_library(config_core src/model_config.cpp)
target_include_directories(config_core PUBLIC include)
target_compile_features(config_core PUBLIC cxx_std_17)

add_executable(config_cli src/main.cpp)
target_link_libraries(config_cli PRIVATE config_core)

include(CTest)
if(BUILD_TESTING)
    add_executable(config_test tests/config_test.cpp)
    target_link_libraries(config_test PRIVATE config_core)
    add_test(NAME config_test COMMAND config_test)
endif()
```

`PUBLIC include` означает, что заголовки нужны и библиотеке, и использующим её целям. `PRIVATE config_core` означает, что только `config_cli` зависит от библиотеки. У зависимостей есть три области видимости: `PRIVATE` — внутри цели, `INTERFACE` — у её пользователей, `PUBLIC` — в обоих местах. Так зависимости остаются явными без глобальных `include_directories(...)` и `add_definitions(...)`.

В каталоге [cmake_demo](cmake_demo/) лежит законченный пример с библиотекой, CLI и тестом. Соберите его из каталога урока:

```bash
cmake -S cmake_demo -B cmake_demo/build -DCMAKE_BUILD_TYPE=Debug
cmake --build cmake_demo/build
ctest --test-dir cmake_demo/build --output-on-failure
```

Найдите в примере, какие файлы компилируются для каждой цели. Поменяйте реализацию `normalize_name()` и убедитесь, что тест обнаруживает ошибку. Затем верните исправление.

### Несколько каталогов

Для растущего проекта можно вынести библиотеку в `core/CMakeLists.txt` и подключить её через `add_subdirectory(core)`. Внутри `core` объявляется `add_library(...)`, а корневой файл связывает `target_link_libraries(app PRIVATE core)`. Это тот же принцип, который применялся в прошлогоднем `2025/cpp/assignments/lesson04/cmake_example_module_A_B/`. Отдельный `CMakeLists.txt` полезен, когда у каталога есть собственная цель и набор зависимостей.

### Подключение внешней библиотеки

Для JSON в заданиях используется `nlohmann::json`. Если библиотека установлена и доступна CMake, подключите её так:

```cmake
find_package(nlohmann_json 3.11 CONFIG REQUIRED)
target_link_libraries(config_core PUBLIC nlohmann_json::nlohmann_json)
```

Если установленного пакета нет, один из вариантов — `FetchContent`. Он требует доступа к сети при *первой* конфигурации; закрепляйте версию, чтобы результат не менялся неожиданно:

```cmake
include(FetchContent)
FetchContent_Declare(nlohmann_json
    GIT_REPOSITORY https://github.com/nlohmann/json.git
    GIT_TAG v3.11.3
)
FetchContent_MakeAvailable(nlohmann_json)
target_link_libraries(config_core PUBLIC nlohmann_json::nlohmann_json)
```

Выберите **один** способ и укажите его в README проекта. Если публичный заголовок содержит `#include <nlohmann/json.hpp>`, зависимость от JSON тоже должна быть `PUBLIC`; если JSON используется только в `.cpp`, достаточно `PRIVATE`. Готовый пример с `FetchContent` был в прошлогоднем `2025/cpp/assignments/lesson04/cmake_example_json/`.

### Если сборка не получилась

| Сообщение | Что проверить |
| --- | --- |
| `No such file or directory` для своего заголовка | `target_include_directories`, путь и регистр имени файла |
| `undefined reference` / `undefined symbols` | включён ли `.cpp` в библиотеку и есть ли `target_link_libraries` |
| `Could not find ...Config.cmake` | установлен ли пакет или настроен ли `FetchContent` |
| JSON читается из неверного места | текущий рабочий каталог при запуске; передавайте путь аргументом |

Чтобы увидеть команды компилятора, выполните `cmake --build build --verbose`. При смене генератора создайте новый каталог сборки, например `build-ninja/`, вместо повторного использования старого.

## 3. JSON — данные на границе программы

Парсинг JSON проверяет синтаксис, но не смысл данных. Для конфигурации вида

```json
{
  "model": "local-model.gguf",
  "context_size": 2048,
  "temperature": 0.7
}
```

нужно отдельно проверить: корень — объект; обязательные ключи есть; `model` — непустая строка; `context_size` — целое число в выбранном диапазоне; `temperature` — число в диапазоне `[0, 2]`. Документируйте границы в собственном проекте. Значения `null`, массив вместо объекта, дробное `context_size` и отсутствующее поле — разные ошибки. Не превращайте их молча в значения по умолчанию.

```cpp
#include <nlohmann/json.hpp>

using nlohmann::json;

json request = {
    {"model", "local-model"},
    {"messages", json::array({
        {{"role", "user"}, {"content", "Привет"}}
    })}
};

const auto parsed = json::parse(text); // может выбросить parse_error
if (!parsed.is_object() || !parsed.contains("context_size") ||
    !parsed.at("context_size").is_number_integer()) {
    throw std::runtime_error("context_size должен быть целым числом");
}
```

После проверки типа преобразуйте значение в C++ и проверьте диапазон. Для полей ответа модели двигайтесь по вложенным объектам и массивам только после проверки их формы и индексов. Исключения `nlohmann::json` ловите на границе приложения, чтобы пользователь видел понятное сообщение, а программа завершалась с ненулевым кодом. Логику проверки удобнее вынести в функцию, которую можно протестировать без сети и модели.

## 5. Задание через GitHub: собираемый прототип

Сделайте небольшое **CLI-приложение для подготовки запроса к локальной модели**. Оно принимает путь к JSON-конфигурации и текст запроса, проверяет конфигурацию, строит JSON-запрос с `messages` и печатает его в стандартный вывод. Подключение к модели и HTTP на этом уроке не нужны: их добавим позже. Можно использовать функции из решённых задач, но их необходимо встроить в многофайловый проект.

Создайте каталог `assignments/lesson04/<фамилия>/`:

```text
<фамилия>/
├── CMakeLists.txt
├── README.md
├── config.example.json
├── include/             # интерфейс проверки конфигурации и построения запроса
├── src/                 # реализации и отдельный main.cpp
└── tests/               # минимум один исполняемый тест
```

### Обязательная функциональность

1. CLI принимает путь к конфигурации и текст пользователя аргументами, например `./model_request config.example.json "Привет"`. При неверном числе аргументов печатает подсказку и возвращает ненулевой код.
2. Конфигурация содержит как минимум имя модели, размер контекста и температуру. Проверяйте отсутствие и тип каждого поля, диапазоны чисел и пустую строку модели. Ошибки файла, синтаксиса JSON и структуры конфигурации должны быть понятными и различимыми.
3. Логика конфигурации и построения запроса находится вне `main.cpp`, в `.hpp` и `.cpp`. `main.cpp` отвечает за CLI, чтение файла и сообщения об ошибках. В коде есть осмысленное пространство имён.
4. CMake создаёт библиотечную цель для логики, исполняемую цель для CLI и тестовую цель, использующую ту же библиотеку. Укажите C++17 и зависимость от `nlohmann_json::nlohmann_json` на нужных целях. Зарегистрируйте тест через CTest.
5. Тесты без сети и модели проверяют как минимум корректную конфигурацию, пропущенное поле, неверный тип, число вне диапазона и структуру созданного запроса. Тест может состоять из `assert` или явных проверок с кодом возврата; если используете `assert`, не запускайте его в конфигурации с `NDEBUG`.
6. README проекта содержит требования, выбранный способ получения JSON-библиотеки, точные команды конфигурации, сборки, тестирования и запуска, пример входа и ожидаемый результат, а также краткую схему целей и файлов.

Пример проверки из каталога вашего проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
./build/model_request config.example.json "Привет"
```

Путь к исполняемому файлу зависит от генератора и выбранного имени цели; укажите фактическую команду в своём README. Для Visual Studio и Xcode потребуется `--config Debug` и соответствующий подкаталог при запуске.

### Дополнительное задание для тех, кто уже закончил

Добавьте вторую библиотечную цель, например для валидации ответа модели, в отдельном каталоге с собственным `CMakeLists.txt`. Подключите её через `add_subdirectory` и протестируйте на двух ответах: корректном и содержащем неверную вложенную структуру. Покажите в README граф зависимостей целей. Это расширение не требует сети или API-ключа.

### Что сдавать и показывать на разборе

Отправьте отдельный pull request с каталогом `<фамилия>/`. Не добавляйте `build/`, исполняемые файлы, модели, секретные ключи и личные конфигурации. На разборе покажите сборку с нуля, успешный `ctest`, один ошибочный вход и объясните, почему логика вынесена в библиотеку и как к ней подключён JSON.

## Использование ИИ

ИИ разрешён для объяснения ошибок CMake, поиска пропущенных проверок JSON и предложения тестовых входов. Проверяйте каждую предложенную команду и изменение: на разборе нужно уметь объяснить состав целей, область видимости зависимостей и поведение программы на неверном входе.
