# Lesson 06. Coding Agent и Tool Calling

На этом занятии мы познакомимся с coding agent — программой, которая использует
языковую модель не только для генерации текста или кода, но и для выполнения
действий в проекте.

Агент сможет:

- смотреть структуру проекта;
- читать исходные файлы;
- запускать CMake;
- собирать проект;
- запускать тесты и программы;
- получать сообщения компилятора;
- принимать решение о следующем действии;
- исправлять найденные ошибки;
- проверять результат.

В дальнейшем такой агент можно использовать при работе над индивидуальным проектом.

---

## 1. Чем агент отличается от обычного чата

Обычная языковая модель работает примерно так:

```text
пользователь
    ↓
   LLM
    ↓
текстовый ответ
```

Например:

```text
Почему этот C++ код не компилируется?
```

Модель видит только тот код, который пользователь передал ей в запросе.

Coding agent работает иначе:

```text
пользователь
    ↓
   LLM
    ↓
tool call
    ↓
программа выполняет действие
    ↓
результат возвращается LLM
    ↓
LLM принимает следующее решение
```

Таким образом модель может взаимодействовать с реальным проектом.

Например:

```text
Пользователь:
Собери проект и исправь ошибку.
```

Модель может решить:

```text
1. Посмотреть файлы проекта.
2. Прочитать CMakeLists.txt.
3. Запустить CMake.
4. Запустить сборку.
5. Проанализировать сообщение компилятора.
6. Исправить файл.
7. Повторить сборку.
8. Запустить программу или тесты.
```

---

## 2. Что такое Tool Calling

LLM сама по себе не умеет читать файлы или запускать программы на компьютере.

Вместо этого ей можно описать доступные **tools** — инструменты.

В нашем агенте есть инструмент:

```text
run_command(command)
```

Он позволяет выполнить команду в терминале проекта.

Мы передаём модели описание инструмента:

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "run_command",
            "description": "Run a command in the current project directory",
            "parameters": {
                "type": "object",
                "properties": {
                    "command": {
                        "type": "string"
                    }
                },
                "required": ["command"]
            }
        }
    }
]
```

Важно: это **не выполнение функции**.

Мы только сообщаем модели:

> У тебя есть инструмент с именем `run_command`.
> Если он тебе понадобится, верни его имя и аргументы.

Например модель может вернуть:

```json
{
    "name": "run_command",
    "arguments": {
        "command": "cmake -S . -B build"
    }
}
```

Это называется **tool call**.

---

## 3. Кто на самом деле выполняет команду

LLM ничего не запускает самостоятельно.

Tool call получает наша Python-программа.

Она вызывает:

```python
subprocess.run(...)
```

и реально выполняет команду на компьютере.

Например:

```bash
cmake --build build
```

Результат:

```text
exit_code=2

stderr:
main.cpp:4:38: error: expected ';' after expression
```

возвращается обратно модели.

Теперь LLM уже знает, что произошло, и может решить, что делать дальше.

Например:

```text
В main.cpp пропущена точка с запятой.
Нужно исправить файл и повторить сборку.
```

## 4. Agent Loop

Главная часть агента — цикл.

Упрощённо он выглядит так:

```python
while True:
    response = llm(messages)

    if response.tool_call:
        result = execute_tool(response.tool_call)
        messages.append(result)
    else:
        print(response.content)
        break
```

Таким образом агент работает итеративно:

```text
LLM
 ↓
действие
 ↓
результат
 ↓
LLM
 ↓
новое действие
 ↓
результат
 ↓
...
```

Это называется **agent loop**.

Большинство современных coding agents используют похожий принцип.

Codex CLI, Claude Code, OpenCode, Cline и другие системы значительно сложнее,
но базовая идея остаётся той же:

```text
LLM + tools + цикл выполнения
```

## 8. Почему нельзя разрешать агенту любые команды

Наш агент выполняет команды, предложенные языковой моделью.

Если разрешить совершенно произвольные команды, модель теоретически может
выполнить что-нибудь нежелательное:

```bash
rm ...
```

или изменить файлы за пределами проекта.

Поэтому реальный coding agent должен ограничивать доступные действия.

В учебной версии используется **white list** — список разрешённых команд.

Например:

```text
ls
find
cat

cmake
ctest
make
ninja

g++
clang++
gcc
clang
```

Команды вроде:

```text
rm
sudo
ssh
scp
curl
wget
```

агент выполнять не должен.

Также желательно запретить shell-конструкции:

```text
;
&&
||
|
>
<
$()
```

Поэтому вместо одной команды:

```bash
cmake -S . -B build && cmake --build build
```

агент должен сделать два tool call:

```text
cmake -S . -B build
```

а затем:

```text
cmake --build build
```

Это одновременно безопаснее и позволяет лучше видеть логику работы агента.

---

## 9. Пример white list в Python

Ниже один из простых вариантов ограничения команд:

```python
import shlex
import subprocess

ALLOWED_COMMANDS = {
    "ls",
    "find",
    "cat",
    "cmake",
    "ctest",
    "make",
    "ninja",
    "g++",
    "clang++",
    "gcc",
    "clang",
}

def run_command(command):
    args = shlex.split(command)

    if not args:
        return "ERROR: empty command"

    program = args[0]

    if program not in ALLOWED_COMMANDS:
        return f"ERROR: command '{program}' is not allowed"

    result = subprocess.run(
        args,
        capture_output=True,
        text=True,
    )

    return (
        f"exit_code={result.returncode}\n"
        f"stdout:\n{result.stdout}\n"
        f"stderr:\n{result.stderr}"
    )
```

Здесь `shell=True` не используется.

Это важно: модель не может склеить несколько команд через `&&`, `;` или другие
shell-операторы и выполнить то, что не входит в разрешённый список.

## 10. Задание

Запустите агента на тестовом C++ проекте.

В проекте намеренно присутствует ошибка.

Попросите агента:

```text
Собери этот C++ проект. Если сборка не проходит, найди причину, исправь её и проверь, что проект успешно собирается.
```

Проследите за последовательностью tool calls.

Ответьте на вопросы:

1. Какие действия агент выполнил до первой попытки сборки?
2. Как агент получил информацию об ошибке компилятора?
3. Как модель узнала содержимое проекта?
4. Чем tool call отличается от обычного текстового ответа модели?
5. Почему после выполнения команды её результат необходимо снова передавать LLM?
6. Почему агент работает в цикле?
7. Какие риски возникают, если дать модели неограниченный доступ к shell?

## 11. Важно

Coding agent не является заменой пониманию программы.

Автор проекта отвечает за:

- архитектуру;
- корректность программы;
- безопасность;
- тестирование;
- понимание внесённых изменений.

Если агент написал код, студент должен быть способен объяснить этот код
и обосновать сделанные решения.

## 11. Практическое задание на своём проекте

Возьмите проект из предыдущего занятия и запустите агента в корне проекта.

### Шаг 1. Анализ проекта

Попросите агента:

```text
Изучи этот проект.

1. Опиши структуру проекта.
2. Объясни назначение основных файлов.
3. Найди потенциальные ошибки или проблемные места.
4. Ничего пока не изменяй.
```

Проверьте, какие файлы и команды агент использовал для анализа проекта.

### Шаг 2. Проверка проекта

Попросите агента:

```text
Собери проект и запусти тесты, если они есть.

Если обнаружатся ошибки:
1. объясни причину;
2. исправь их;
3. повторно собери проект;
4. проверь результат.
```

После работы агента просмотрите внесённые изменения.

Если проект находится под Git, используйте:

```bash
git diff
```

и убедитесь, что понимаете каждое изменение.

### Шаг 3. README

Попросите агента подготовить или улучшить `README.md` проекта.

Например:

```text
Изучи проект и подготовь README.md.

README должен содержать:

- краткое описание проекта;
- структуру проекта;
- инструкции по сборке;
- инструкции по запуску;
- пример использования;
- описание тестов, если они есть.

Не придумывай возможности, которых в проекте нет.
```

Проверьте созданный README и исправьте неточности, если они появились.

### Шаг 4. Code review

Попросите агента провести review:

```text
Проведи code review этого проекта.

Обрати внимание на:

- ошибки и потенциальный undefined behavior;
- управление ресурсами и RAII;
- лишние копирования;
- const correctness;
- структуру классов;
- обработку ошибок;
- читаемость кода;
- CMake;
- тестирование.

Сначала только перечисли замечания.
Не изменяй файлы.
```

Выберите одно или несколько замечаний агента и решите, действительно ли они обоснованы.

После этого можно попросить агента исправить выбранные проблемы.

## Что нужно показать преподавателю

В результате работы нужно уметь показать:

1. Какие tool calls выполнял агент.
2. Какие ошибки или проблемы он нашёл.
3. Какие файлы он изменил.
4. `git diff` после работы агента.
5. Какие предложения агента вы приняли.
6. Какие предложения агента вы отвергли и почему.
7. Итоговый `README.md`.

Главное требование: понимать и уметь объяснить все изменения,
которые агент внёс в проект.
