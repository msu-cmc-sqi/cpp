# Программа практикума 2026

## Идея курса

Это проектный практикум, а не последовательность из заранее заданных лекций. В начале семестра мы повторим необходимые инструменты C++, после чего необходимо выбрать собственную задачу, найти подходящую модель на Hugging Face и постепенно превратить прототип в законченное приложение.

На занятиях мы обсуждаем архитектуру, разбираем возникшие технические проблемы, проводим code review и показываем промежуточные результаты.

## Формат

- продолжительность — один семестр, ориентировочно 12–14 занятий;
- основной язык — C++17/20;
- при выборе модели желательно ориентироваться на базовый сценарий, который можно запустить на обычном ноутбуке; платный API или специализированная видеокарта могут использоваться для дополнительных возможностей проекта;

Форма итоговой аттестации — зачёт с оценкой.

## Общий старт

Первые занятия посвящены общей инженерной базе:

1. Git, ветки, pull request и организация совместной работы.
2. ООП, RAII, владение ресурсами и современный C++.
3. Возможности C++17/20, стандартная библиотека и шаблоны.
4. CMake, структура проекта, внешние зависимости и тестирование.
5. JSON, HTTP и взаимодействие с локальным сервисом.

Эти темы не обязательно занимают ровно пять отдельных занятий: знакомые группе части можно пройти быстрее, а сложные — разобрать подробнее.

## Выбор проекта

После общего старта необходимо предложить собственный проект и определить:

- какую проблему решает приложение;
- кто его пользователь;
- что в проекте должна делать модель, а что — обычный код;
- какие данные потребуются;
- на каком ноутбуке будет запускаться проект;
- какие 2–3 модели с Hugging Face подходят для задачи;
- как можно проверить, что приложение действительно работает полезно.

Идея обсуждается с группой. После короткой защиты и полученных замечаний при необходимости можно уменьшить или уточнить объём проекта.

## Проектные циклы

Дальнейшая работа проходит короткими циклами. Каждый цикл включает:

1. постановку небольшой достижимой цели;
2. самостоятельную реализацию;
3. демонстрацию работающего результата;
4. code review или обсуждение архитектуры;
5. план следующей итерации.

На занятиях могут появляться короткие объяснения по темам, которые нужны текущим проектам:

- поиск моделей на Hugging Face и чтение model card;
- GGUF, квантование и запуск через `llama.cpp`;
- проектирование интерфейса инференса;
- structured output и JSON Schema;
- embeddings и RAG;
- tool calling и MCP;
- асинхронные операции, streaming и отмена запросов;
- кэширование, логирование и измерение производительности;
- тестирование недетерминированных систем;
- безопасность и проверка действий модели.

Это перечень возможных тем, а не обязательный порядок. Прежде всего необходимо изучать то, что требуется конкретному проекту, а затем делиться результатами с группой.

## Выступления в течение семестра

В течение семестра необходимо несколько раз выступить перед группой. Все выступления индивидуальные и учитываются при выставлении итоговой оценки.

### Защита идеи

Коротко рассказать о задаче, пользователе, моделях-кандидатах, ограничениях ноутбука и предполагаемом результате.

### Технический разбор

Объяснить один самостоятельно изученный вопрос: например, устройство GGUF, выбор квантования, embeddings, JSON Schema, streaming или способ оценки качества. Важно не пересказать документацию, а показать небольшой работающий пример и выводы для своего проекта.

### Промежуточная демонстрация

Показать один полностью работающий пользовательский сценарий, текущую архитектуру и проблему, которую ещё предстоит решить.

### Финальная защита

Продемонстрировать приложение, объяснить ключевые архитектурные решения, показать результаты тестирования и измерений, а также разобрать несколько случаев, когда модель ошибается. На защите необходимо самостоятельно ориентироваться в своём коде и отвечать на вопросы по реализации.

## Возможные контрольные точки

Точные даты определяются по ходу курса, но к концу семестра у проекта должны появиться:

- сформулированная задача и согласованный объём;
- обоснованный выбор модели;
- минимальный работающий прототип;
- один законченный пользовательский сценарий;
- тестовые примеры и измерения;
- воспроизводимая сборка и инструкция запуска;
- финальная демонстрация.

## Зачёт с оценкой

Итоговая оценка является индивидуальной и складывается из следующих частей:

- постановка задачи и самостоятельность принятых решений;
- качество и сложность реализации на C++;
- обоснованность выбора модели;
- регулярность работы и промежуточные демонстрации;
- технический доклад;
- тестирование, измерения и понимание ограничений проекта;
- качество финальной защиты и ответы на вопросы.

Наличие работающей программы само по себе не гарантирует высокую оценку. На защите необходимо объяснить устройство проекта, назначение основных компонентов, причины ключевых решений и подтвердить самостоятельность выполнения работы.

Подробные технические ориентиры находятся в [требованиях к итоговому проекту](PROJECT.md). Они задают ожидаемое качество результата, но не ограничивают тему и архитектуру проекта одним шаблоном.
